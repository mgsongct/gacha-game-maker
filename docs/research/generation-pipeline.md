# 게임 생성 파이프라인: 계측과 개선안 (제안 단계)

새 게임 한 개가 만들어지는 과정(세계관 → 대원 → 오프닝 → 1장 → 스킬)을 **가짜 AI로 계측**하고, 실패를 일부러 넣어 동작을 확인한 결과와 개선안입니다. 아직 구현하지 않은 제안이라 "이 앱의 결정" 대신 **제안** 절을 둡니다. 종합 점검은 [maker-review.md](maker-review.md).

## 0. 요약

| 항목 | 값 (2026-11-03, 빌드 2026.11.03.17) |
|---|---|
| 새 게임 1개(대원 6명, 자율 모드)의 기본 호출 | **4회**(세계관·대원·오프닝·1장, 모두 `complex`, 순차), 보낸 글 **28,026자** |
| 대원 생성 프롬프트 | **15,786자** 중 스킬 규칙 10,418자 + 스킬 스키마 4,332자(**93%**) |
| 인라인 스킬이 규칙에 안 맞을 때 | 대원마다 스킬 설계 최대 **6회** → 6명이면 최대 **36회 · 133,836자** 추가 |
| 다음 장 구성 프롬프트 | 장이 1→12개로 늘어도 **26,223~27,031자**(상한 유지). 그중 새 대원 스킬 규칙·스키마 **14,890자(55%)** |
| 프롬프트 캐싱 | **쓰지 않음**(`cache_control` 등 0건. `cache:false` 옵션은 넘기지만 읽는 곳 없음) |
| 확인된 결함 | ① 세계관 필드가 빠지면 **샘플 게임 내용이 섞임** ② 스킬 설계 전에 저장돼 **임시 스킬이 굳음** ③ 인원·이름 중복·등급·세력 검증 없음 ④ 이후 장에 샘플 상수 ⑤ 실패해도 백그라운드 호출 계속 |

## 1. 현황 조사

### 1-1. 방법

- `build/test.mjs` 24번처럼 브라우저에서 앱을 띄우고(외부 요청 차단), AI 프로필을 하나 등록한 뒤 **`aiOne`을 가로채** 실제로 공급자에게 보낼 글(`llmWrap`으로 지침·교훈·`JSON만 출력`까지 붙은 최종본)을 기록했습니다. 응답은 단계별 고정 JSON.
- `buildNewGameDraft(btn, {mode:'auto', auto:'등불섬 판타지', n:6}, …)` 한 번 = 새 게임 하나. 저장은 `appStorage.commitRecords`를 감싸 잡았습니다.
- 응답이 즉시 오므로 **시간은 실제 AI 대기가 아니라 앱 쪽 처리·재시도 간격**만 뜻합니다.
- 계측 스크립트는 저장소에 넣지 않았습니다. 같은 방법을 회귀 테스트로 옮기는 것을 §3-9에서 제안합니다.

- `ngStep`의 통과 기준은 "필요한 키가 있는가"뿐입니다(a: `r.title&&r.world`, b: `r.chars.length`).

### 1-4. 실패를 넣었을 때

| 시나리오 | 호출 | 새 게임 | 초안(이어 쓰기) | 사용자에게 보인 것 |

| 대원 6명 요청에 **3명**(이름 `하나` 중복, 역할 `healer`, 등급 9, 이름 80자, 모르는 세력, 빈 프로필) | 22 | **만들어짐** | – | 아무 경고 없음 |

- **세계관 누락**: 새 게임의 플롯이 "1부의 축: 헬릭스는 분화구 아래 잠든 '첫 번째 별'을…", 설정이 "낙성의 밤 이후 에덴포트는…", 세력이 새벽등대·헬릭스 컨소시엄·잔광·회색구 시민회·회색구 연합(샘플 5개)에 새 세력이 덧붙은 목록, 재료 던전이 "전투 기록 회수/…/성핵 코어 정제"로 저장됐습니다. 원인은 `ng.world=Object.assign(clone(DEFAULT_WORLD),a.world||{})`(`0250:222`) — 빠진 필드가 샘플 값으로 남습니다. 이 플롯은 `ctx()`를 거쳐 이후 모든 생성에 "메인 플롯"으로 들어갑니다.
- **대원 3명**: `하나`가 두 명(대본 `하나: …`의 화자를 구분할 수 없음), `healer` → `atk`, 등급 9 → 1, 이름 20자로 자름, `없는세력`은 **플레이어블 세력으로 새로 추가**(`0250:230`), 빈 프로필 그대로. 같은 방식으로 대원의 세력 이름이 세계관 목록과 조금만 달라도(오타) 새 세력이 생깁니다.
- 1장·오프닝 실패 때도 그 사이 스킬 설계 호출이 36~37회 나갔습니다. 다시 누르면 초안의 대원 결과로 `cleanChar`가 다시 돌아 **같은 호출이 또 나갑니다**.
- 어느 실패든 끝에 "생성 기능이 좋아졌어요… 104개를 업그레이드할 수 있어요"가 뜹니다 — 실패와 무관한 **샘플 게임**의 점검 결과입니다([sample-onboarding.md](sample-onboarding.md)). 새 게임도 `auditSeen`을 찍지 않아(`0535-content-audit.js:99`에서만 기록) 오프닝 뒤 다시 켜면 같은 알림이 뜹니다(`:116`).

| 검증 → 수리 | 스키마로 표현 못 하는 제약은 로컬에서 검증하라는 것이 공급자 문서의 권고[4]. Self-Refine은 7개 과제 평균 약 +20%p, 반복할수록 이득 감소[7] | 빠진 부분만 다시 요청(이미 있는 `auditAIFill` 방식), 수리는 1~2회로 제한 |
| 기억·일관성 | 대화 8턴 안에 시스템 프롬프트 지시에서 벗어남(지시 표류)[8] | 캐릭터·세계 바이블을 호출마다 **같은 앞부분**으로 넣는 지금 방식이 맞고, 그 앞부분을 캐싱 대상으로 |
| 프롬프트 캐싱 — Anthropic | 앞부분이 바이트 단위로 같아야 적중, 순서 tools → system → messages. 중단점 최대 4개. 쓰기 1.25배(5분)·2배(1시간), 읽기 약 0.1배(Opus 5.5는 0.05배). 최소 길이: Claude Opus 5.5·Sonnet 5.5·Haiku 5.5 등 최신 모델 512토큰, Sonnet 4.6 1,024, **Haiku 4.5 4,096토큰**. 5분 TTL은 읽을 때마다 갱신, 시간은 요청 **시작**부터[9] | 앱 기본 모델: 글 `claude-sonnet-5-5`, 빠른 작업 `claude-haiku-4-5-20251001`(`DEFM` `0020:6`) → 빠른 작업은 4,096토큰 미만이라 캐시가 거의 안 붙음 |
| 프롬프트 캐싱 — 기타 | OpenAI: 1,024토큰 이상 자동, 입력 최대 90%·지연 최대 80% 절감[10] **[미확인: 원문 미열람]**. Gemini 2.5 이상: 암시적 캐시 기본, Vertex 기준 할인 90%[11]. 최소 토큰은 문서마다 달라 **[미확인]** | 공급자 공통으로 "정적 앞부분이 길고 같을 것"만 지키면 자동 캐시도 효과 |
| 토큰 세기 | Anthropic `POST /v1/messages/count_tokens`, 모델마다 다름. `tiktoken` 같은 다른 회사 토크나이저는 Claude 토큰을 적게 셈[12] | 미리 보기는 글자 수 기반 대략치로 시작하고, 정밀값은 공급자 응답의 `usage`를 기록해 보정 |

## 4. 수치·공식

- 기본 비용(보낸 글) ≈ 세계관 3.2K + 대원 15.8K + 오프닝 3.4K + 1장 5.7K = **28.0K자**. 장마다 구성 26~27K자 + 스테이지별 대본 요청.
- 스킬 재시도 상한 = 대원 수 × 6 × 약 3.7K자. 6명이면 133.8K자(기본의 약 4.8배).
- 캐싱 효과(입력, 글자 비례 근사): 정적 S, 동적 D, 5분 안에 같은 앞부분 요청 n번이면
  - 캐시 없음: `n × (S + D)`
  - 캐시: `1.25·S + (n−1)·0.1·S + n·D`
  - 예) 장 구성 1회 + 스테이지 대본 4회(n=5), S=12K, D=15K자 → 135K → 94.8K(**약 30% 감소**). 대원 생성 재시도(같은 요청 3회, S=15K, D=0.8K) → 47.4K → 24.2K(약 49% 감소).
  - 실제 효과는 토큰 수와 공급자 할인율로 다시 계산(Anthropic은 `usage.cache_read_input_tokens`로 확인).

## 5. 확장 아이디어

- 단계 확인 모드: 세계관 카드·대원 카드를 보여 주고 "계속 / 이 단계만 다시"(초안의 `DR.r[k]`만 지움). 이어 쓰기 키를 단계별로 나눠 한 글자 수정에 전체를 다시 만들지 않게
