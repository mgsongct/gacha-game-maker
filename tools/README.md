# tools — 자기점검·정적분석

tree-sitter(`web-tree-sitter` + `tree-sitter-javascript`)로 소스를 구문 트리로 읽고, ast-grep(`@ast-grep/napi`) 패턴으로 품질 규칙을 찾아요. 빌드와 같은 순서로 `src/main/`을 한 스크립트로 이어 붙여 분석하고(이 앱은 main이 한 스크립트라 파일끼리 함수를 바로 부름), 결과의 줄 번호는 원본 파일로 돌려 줘요.

분석 대상: `src/main/`(한 스크립트) · `src/modules/**` · `src/boot/*.js` · `src/index.html` · **`src/style/*.css`**(ast-grep CSS) · **부속 파일** `www/sw.js` · `proxy/**` · `build/*.mjs` · `tools/**`(JS 파싱) · `pc/*.py`(python3가 있으면 구문 검사)

```bash
npm ci --prefix tools
node tools/check.mjs            # 요약 + tools/out/report.md · flow.mmd · report.json
node tools/check.mjs --strict   # 오류가 있거나 기준선보다 새로 생기거나 나빠진 항목이 있으면 exit 1 (CI)
node tools/check.mjs --diff HEAD          # 이번 변경으로 새로 생김·나빠짐·해결 (git 기준 트리에 같은 분석을 돌려 비교 → out/diff.md)
node tools/check.mjs --update-baseline    # 줄었을 때 기준선(tools/baseline.json) 낮추기 — 늘었으면 거부(코드를 고침)
node tools/test.mjs             # 도구 자체 검사
node tools/fix.mjs [--apply]    # 안 쓰는 함수·변수·액션 case 정리(기본은 미리 보기, 지운 뒤 생긴 것까지 되풀이)
```

생성 기능과 **생성된 게임**의 QA·플레이 점검(브라우저로 실제 앱을 돌림)은 [play/README.md](play/README.md): `generate.mjs`(글 AI 응답을 파일로 주고받으며 게임 생성·재생) · `qa.mjs` · `shots.mjs` · `faults.mjs` · `test.mjs`.

게임 데이터 키(G.meta.*·G.world.*·G.*·P().*)마다 **누가 언제 쓰는지**를 원안(포크 전, 기본 `49cec7a` — 원본 index.html을 src/로 나눈 커밋)과 지금 트리에서 뽑아 비교해요(`lib/lifecycle.mjs`, 결과 `out/lifecycle.md`).
- 단계: **생성**(newGame·buildNewGameDraft … 새 게임 초안, 만드는 중인 `ng.*` 포함) · **실행 중 AI**(`liveTick` — 게임이 구동되는 동안 시즌·장·이벤트·픽업·의상·톡을 AI가 만드는 원안의 경로) · **사용자**(`handle*Action` 처리기와 최상위 이벤트 리스너가 부르는 함수) · **불러오기**(fix·defaults·applyMeta)
- 포크가 더한 키(원안에 없던 키)가 원안의 생성·실행 경계 어디에 붙었는지: 아무 단계도 안 씀 · 사용자 조작으로만 씀 · 생성·실행 중 AI 밖
- `--why <키>`: 단계 시작점에서 그 키를 쓰는 함수까지 가장 짧은 호출 경로(예: `실행 중 AI: liveTick → liveFill → auditFixOne → AUDIT_RULES.run → spotsAuto`) — 결과를 설명하고 오탐을 가릴 때
- 함수를 담은 최상위 표(`AUDIT_RULES`의 `fix.run`·`test` 등)는 속성별 의사 함수(`AUDIT_RULES.run`)로 그래프에 들어가요(`lib/graph.mjs`). 그 속성을 멤버로 호출하는 함수만 이어지고, 표를 참조만 하는 곳은 잇지 않아요
- 한계: 동적 키 쓰기(`P()[k]=v`)는 못 따라가요(아무도 안 씀으로 나옴 — 도구 문제인지 코드 문제인지 따로 가림)

## 코드 옮기기 (`node tools/move.mjs --to <src 파일> [--head 제목] 이름,… [--dry]`)

최상위 선언(function·const·let — 바로 위 `//` 주석째)을 이름으로 찾아 다른 src 파일로 원문 그대로 옮겨요. 과잉 분할·기능 섞임·기능 분산(자연 경계)을 고쳐 한 기능을 한 모듈로 모을 때. 옮긴 뒤 불러올 때 아직 없는 이름(TDZ)이 생기면 되돌려요. 프롬프트 코드는 `tools/prompts-move.mjs`(`--req` 요청 조립 식 — 지역 값·화면 입력은 인자로, `--fns --only` 조립 함수, 목록 파일 — 지시문을 스튜디오 조각으로).

## 구버전·미비 생성 게임 감지·보완 (`node tools/wiring.mjs` 표 · `node tools/play/upgrade.mjs`)

생성기·실행기가 바뀌어도 예전 빌드로 만든·빠진 데 있는 게임을 지금 앱이 알아채고 채우는지. 정적(`tools/lib/upgrade.mjs`): 포크 기능이 새로 만든 키·필드(원안 생성기가 쓰던 키는 원안 코드에서 같은 방법으로 구해 뺌)마다 불러오기 이전(`fix`가 씀) · 콘텐츠 점검 규칙(`AUDIT_RULES`의 test·fix가 읽는 키·필드, 판 since) · 실행 중 AI · 없으면 기본값 — 경로 없음이 늘면 배선 래칫 실패, 기본값으로만은 주의. 동적: 항목마다 그 데이터만 뺀 예전 게임(점검 판·생성 판 0)을 지금 빌드에 불러와 점검 알림·점검 발견·자동 보완(앱의 liveFill + 규칙 고치기, 가짜 글 AI) 뒤 채워졌나(가짜 글 AI는 형식 견본을 그럴듯한 답으로 채워 답함 — `lib/combos.mjs` `fakeAnswer`: 빈 글 채움·고르기 견본 하나씩·객체 하나짜리 목록은 가짓수만큼, 앱의 답 검사를 통과해 채우기까지 가게), 보완 뒤 다른 점검 항목이 새로 생기거나 늘었나(자동 채움 대상이 아니면 "새 문제" — 종료 코드 1, 대상이면 "이어서 채울 항목") — 정적 표는 후보, 동적이 판정(실행 중 AI 쓰기가 다른 조건에서만 일어나는 경우를 잡음).

## 포크 기능 배선 점검 (`node tools/wiring.mjs [--strict] [--update-baseline]`)
포크 기능의 데이터가 **원안의 생성 경계**(생성 = 세계관·기본 원칙 / 실행 중 AI = 시나리오·콘텐츠 / 사용자)에 맞게 만들어지는지, 생성된 게임에 실제로 들어갔는지를 tree-sitter로 맞춰 봐요(`lib/wiring.mjs`, 목록 `fork-features.json`, 결과 `out/wiring.md`). 단계 구분은 데이터 생애주기(`lib/lifecycle.mjs`)와 같아요.

| 단계 | 방법 |
|---|---|
| 기능의 범위 | `fork-features.json`의 커밋마다 그 커밋 트리 − 부모 트리의 최상위 함수. git 트리의 `src/`만 `out/ref-src/<sha>/`에 풀어 캐시 |
| 기능이 읽는 데이터 | 그 함수들이 읽는 `G.meta.*`·`G.world.*`·`G.*`·`P().*` 키 + 게임 컬렉션 콜백·찾기 함수에 묶인 변수에서 읽는 **원본에 없던 필드** |
| 누가 만드나 | 생성 단계(새 게임 초안)의 `ng.*`·`G.*` 대입·`Object.assign` 리터럴·프롬프트 스키마(`부모/키`), 실행 중 AI 단계(liveTick 경로)의 쓰기, 사용자 조작 처리기의 쓰기 |
| 기능 쪽 기본값 | `키 \|\| 기본값`·`Object.assign(기본값, 키)`·`if(!x.키) x.키 = 기본값` — 빈 값인지 쓸 만한 값인지 리터럴로 판단. 원본 샘플 기본값은 `DEFAULT_META`·`DEFAULT_WORLD`·`DEFAULT_PROG` 리터럴 |
| 생성된 게임 | `pc/data`(PC 서버 data 폴더)의 게임(샘플 main 제외) — 값·빔·기본값·없음 |

판정: **P0** 어느 단계도 만들지 않아 기능이 비어 있음 · **P1** 사용자 조작으로만 만들어짐(자동이 기본) / 생성 단계 키인데 생성 게임에 없음 / 공통·샘플 기본값으로만 시작 / 기능이 읽는 새 필드를 생성·실행 중 AI가 만들지 않음. **실행 중 AI가 만드는 키는 생성 직후 없어도 정상.** 생성기가 정할 것이 아닌 키(사용자 설정)·공통 기본값으로 충분한 키·플레이 중 생기는 필드는 `fork-features.json`의 `userKeys`·`defaultOk`·`runtimeFields`에 **사유와 함께**. 판정은 `baseline.json`의 `wiring`으로 래칫(CI `--strict`).

## 이름 규칙 (`node tools/names.mjs [--apply] [--strict] [--update-baseline]`)
분석이 헷갈리는 원인(같은 지역 이름 `b`·`e`·`x`가 배너·버튼·캐릭터, 적·이벤트·오류처럼 여러 종류에 쓰임)을 코드 품질 문제로 보고 정리하는 도구예요(`lib/names.mjs`, 규칙 `naming.json`, 결과 `out/names.md`).
- **자동 모으기**: 종류를 코드로 아는 바인딩만 셈 — 게임 컬렉션 콜백(`G.chars.map(c => …)`·`.stages`·`.enemies`·`G.lib`·`factions()`·`ELEMS` …), 찾기 함수 호출 자체(`const c = charById(…)`, `$('#x')` — `$('#x').value`처럼 호출 결과의 멤버는 아님), 이벤트 리스너 매개변수, catch 매개변수. 이름 × 종류 표
- **규칙**: `naming.json`(게임 엔티티 종류마다 고유 이름, 오류·이벤트 객체는 `e` 공유, DOM 요소 `el`). 자동 제안(가장 많이 쓴 이름)은 보고서에 참고로만
- **모호한 이름**: 규칙 이름이 아니면서 다른 종류에도 쓰이는 이름(`src/` 전체)
- **치환** `--apply`: 범위 안에 새 이름이 이미 있거나, 바깥 범위의 같은 이름을 가리게 되거나, 구조 분해 단축 속성이면 건너뜀. 단축 속성 `{c}`는 `{c: ch}`로. 바꾼 뒤 빌드·테스트
- **래칫**: 파일별 개수를 `baseline.json`의 `names`로(CI `--strict`)

## 위반 래칫 (기준선·변경 비교)
- 모든 발견(오류·경고·복잡한 함수·복잡한 익명 콜백·분배기 case·동기 순환·안 쓰는 코드·되풀이 문자열·빈 catch(파일·종류별 개수)·흩어진 상태·쓰기만 하는 키·발신 없는 처리기·안 쓰는 CSS·도구 메타 점검)을 **줄 번호 없는 키**로 바꿔 비교해요(`lib/ratchet.mjs`). 줄만 밀린 것은 같은 항목
- **새로 생김**(기준에 없던 키) · **나빠짐**(같은 항목의 복잡도·줄·중첩·횟수·개수 증가) · 해결 · 좋아짐
- 기준선 `tools/baseline.json`은 커밋돼 있고, CI의 `--strict`가 새로 생김·나빠짐을 막아요. 점검 항목을 새로 늘려 원래 있던 것이 처음 보이게 됐을 때만 `--update-baseline --force`(커밋 메시지에 이유)
- `--diff <기준>`은 기준 커밋을 `out/ref/<sha>/`에 풀어(git archive) 같은 분석을 돌려요

## 메타 점검 (도구 자체)
- 도구 코드(`tools/**`, `build/*.mjs` — node_modules·out·fixtures·games·reports 제외)도 앱과 같은 규칙으로 봐요: 파싱 오류·빈 catch·복잡한 함수·복잡한 익명 콜백·같은 본문·되풀이 문자열·안 쓰는 함수. 보고서 끝 "도구 자체" 절, 래칫 대상
- 큰 익명 콜백(`page.evaluate(async () => {…})`, `addEventListener('click', e => {…})`)은 이름이 없어 함수 그래프에 안 들어가므로 `complexAnon`이 따로 재요. 이름은 `둘러싼 함수→부른 함수 @파일`

## 규칙 늘리기
- tree-sitter 분석은 `lib/graph.mjs`(구조)·`lib/flow.mjs`(흐름), ast-grep 패턴은 `lib/quality.mjs`의 `sgRules`
- 새 규칙을 넣으면 `test.mjs`의 예시 src에 그 문제를 하나 심고 잡히는지 확인

## 알려진 한계
- 멤버 호출(`obj.method()`)·문자열로 부르는 함수(`window[name]()`)는 그래프에 안 들어가요(안 쓰는 함수 판단은 이름 문자열 검색이라 안전한 쪽)
- 상태 흐름은 `G`·`P()`와 같은 함수 안 별칭만 따라가요. 다른 함수로 넘긴 객체(`c`, `ch`)의 변경은 저장 표시 검사에서 빠져요
- 화면에 안 보이는 설정은 휴리스틱(화면 함수 이름 규칙)이라 내부 표시값이 섞일 수 있어요
- HTML 주입은 글 모양 속성 이름(`.name`·`.desc`…)과 `T()`·`sub()`만 봐요. 지역 변수에 담았다 넣는 글(`const n=c.name; …${n}`)이나 다른 함수가 만든 HTML 조각은 못 따라가요
- DOM id는 정적 문자열만 봐요(`$('#'+id)`처럼 이어 붙인 선택자는 건너뜀). 안 쓰는 CSS 클래스는 이름 검색이라, 문자열을 쪼개 만드는 클래스는 쓰는 것으로 못 볼 수 있어요(목록만, 오류·경고 아님)
- 리스너 누수는 "다른 함수가 부르는 함수"를 여러 번 도는 것으로 봐요. 실제로 한 번만 부르면 경고가 지나칠 수 있어요
